# ADR 0001: agent の操作の制限は、プロンプトではなく環境(能力の有無)で強制する

- 状態: Proposed
- 日付: 2026-11-15

## 要旨

- **決定**: agent にさせない操作は、依頼文の「禁止」ではなく、環境(持たせない認証、叩けるコマンド、OS の分離、外向き通信)で止める。5 つの層(L0〜L4)で重ねて守り、いちばん強い L0「能力を持たせない」を土台にする。
- **現時点でできること**: L0(push・merge・approve の認証を agent に渡さず、決定論の実行者だけが持つ)と L1(harness の役割別 allow / deny)は着手可能。L2 は補助として可能。L3・L4 は将来。
- **未確認の点**: サブエージェントへの権限・サンドボックスの継承、L3(別ユーザー)と herdr のセッション運用の相性、egress filter を namespace 単位にできるか。

## 状況(Context)

複数の agent を人が指揮する運用では、操作の制限は依頼文(プロンプト)の「禁止」で表している。これは文章でしかなく、強制ではない。

- 人が pane で agent に直接頼むと、依頼文の「禁止」は効かない(依頼文を経由しないため)。
- 実例(一般化): 読み取り専用のはずのレビュー担当の agent が、作者の作業ディレクトリを書き換えた。止める仕組みが文章だけだったため。
- 逆向きの実例: push や PR 作成が、禁止の既定と、認証の選ばれ方(実行環境に設定された token が優先される)のせいで、人の手作業になっている。禁止が効いているのではなく、認証の選択が偶然に邪魔をしている状態で、意図した制御になっていない。

人の提案(2026-11-15): 強制は文章ではなく環境で行いたい。今すぐ全部は無理でも、方針として残す。

## 決定(Decision)

「agent ができる操作の上限は、agent が持つ能力で決める」。次の層を重ねる。外側の層ほど強く、迂回しにくい。

| 層 | 何をするか | 強さ | 抜け道 | 着手の可否 |
|---|---|---|---|---|
| L0 能力を持たせない | push・merge・approve の認証を agent に渡さない。公開の操作は、決定論の実行者(ジョブ。人が管理する設定で動き、agent の環境を継承しない)だけが認証を持って行う | 最強(持っていないものは使えない) | 認証が agent の環境や共有の認証ヘルパー経由で見えてしまう場合。実行者への依頼の経路が緩いと、実行者が代行になる | 着手可。既に決定論の実行者(draft PR を作るジョブ)の考え方がある |
| L1 harness の権限設定 | 役割ごとに Claude Code の permissions の allow / deny を分ける(例: レビュー担当は Edit・Write を deny) | 中(組み込みのファイルツールには効く) | Bash 経由の迂回(下の事実を参照)。設定ファイルを agent 自身が書き換えられると外れる | 着手可 |
| L2 コマンドのラッパー・制限した PATH | `gh` や `git` を方針検査つきのラッパーに差し替え、PATH を絞る | 弱〜中 | 実体の絶対パスでの直接呼び出し、別のクライアントや言語の標準ライブラリで同じ API を叩く。単独では不十分 | 補助として可。L0 / L3 と併用が前提 |
| L3 OS の分離 | 役割ごとに別ユーザー、worktree の書き込み権限、サンドボックス(Claude Code の Bash サンドボックスなど) | 強(OS が強制。モデルの判断に依らない) | 設定の穴(除外コマンド、サンドボックス外で動く処理)。運用の複雑さから例外が増える | 将来。サンドボックスは試せる。別ユーザーは未検証 |
| L4 namespace ごとの egress filter | 外向き通信を、役割や namespace 単位で許可先だけに絞る | 強(通信そのものを止める) | 許可先を経由した持ち出し、許可の粒度が粗い場合 | 将来 |

運用の原則:

- 重要な操作ほど内側(L0)で止め、プロンプトの「禁止」は補助(説明と、誤操作の予防)に下げる。
- 止めた操作は、決定論の実行者(人の承認を挟むものを含む)に回す。止めるだけで行き先がないと、人の手作業が増えるだけになる。
- 権限設定や規則のファイルは、agent が書けない場所に置く(書けると L1 が外れる)。

## 現時点でできること・できないこと

事実の確認状態: **確認済み**(出典を付記)/ **未確認** / **推測**。確認日 2026-11-15、Claude Code 2.1.325。

### 確認済み

- Claude Code のサンドボックスは Bash(と PowerShell、Monitor)のコマンドとその子プロセスを対象にする。macOS は Seatbelt、Linux / WSL2 は bubblewrap。既定は無効で、`/sandbox` または設定で有効にする。(出典: Claude Code docs「Sandboxing」)
- サンドボックスは、組み込みのファイル・Web ツール(Read、Edit、Write、WebFetch、WebSearch)、command hook、ローカルの MCP サーバー、apiKeyHelper などの補助コマンドには**適用されない**。これらは permissions の規則で制御する。(出典: 同「Sandboxing」)
- サンドボックスの書き込みは、既定では作業ディレクトリ等に限られる。読み取りは既定で広い(認証情報の置き場所も読める)ため、`denyRead` などで絞る必要がある。ネットワークはドメイン単位の許可リストで絞れる(TLS の中身は見ない)。(出典: 同「Sandboxing」)
- サンドボックスの失敗時の逃げ道がある。非対応環境や依存の欠落では、`failIfUnavailable` を設定しない限りサンドボックスなしで動く。失敗したコマンドのサンドボックス外での再試行(`dangerouslyDisableSandbox`)は、`allowUnsandboxedCommands: false` で禁止できる。除外コマンド(`excludedCommands`)はサンドボックス外で動く。(出典: 同「Sandboxing」)
- 管理設定(managed settings)で緩める設定を無効にでき、リポジトリ側の設定で緩められなくなる。(出典: 同「Sandboxing」「Permissions」)
- Bash の権限規則はコマンド文字列に対するもので、deny / ask は「Claude が普段書く形」を止めるものであり、セキュリティ境界ではない、と公式が明記している。複合コマンド(`&&`、`;`、`|` など)は各部分を検査し、deny は入れ子(サブシェル、コマンド置換)にも掛かる。一方で、同じプログラムを別の形(パス指定、`sh -c` の中など)で呼ぶと deny に掛からない。引数を絞る規則は、オプションの順序、プロトコル違い、リダイレクト、変数で外れる。(出典: 同「Permissions」の Bash 規則の節)
- Bash の規則が剥がすラッパーは固定の一覧(`timeout`、`time`、`nice`、`nohup`、`stdbuf` など)で、設定できない。`npx` や `docker exec` のような実行の代行は一覧にないので、規則の意図とずれる。(出典: 同「Permissions」)
- Read / Edit の deny は、組み込みのファイルツール、Bash で認識できる `cat`、`sed`、`tee` などのファイルコマンド、リダイレクトの宛先に適用される。一方、ファイル名を明示せず読むコマンドや、Python / Node のスクリプトが自分でファイルを開く場合には**適用されない**。OS レベルで全プロセスに効かせるにはサンドボックスが必要、と公式が書いている。(出典: 同「Permissions」)
- サブエージェントは `Agent(名前)` の deny 規則で使えるものを制限できる。(出典: 同「Permissions」の Agent の節)
- herdr のサーバーとペインのプロセスは、人と同じ OS ユーザーで動いている(`ps` の表示で確認した)。herdr 自体に、ペイン単位でユーザーを分ける機能は、`herdr --help` と `herdr session --help` の範囲では見当たらない。(出典: 同日の `ps`、`herdr --help`)

### 未確認・推測

- **未確認**: サブエージェントが親の permissions とサンドボックスをそのまま引き継ぐのか(取得した公式ページの範囲では記述を確認できなかった)。引き継ぎが前提だと思い込まず、検証が要る。
- **未確認**: サンドボックスの設定(`denyRead`、書き込み許可)を、役割ごと・worktree ごとに変えて運用した場合の、実際の使い勝手と互換性(動かない既知のツールの一覧が公式にある。git の SSH など)。
- **未確認**: egress filter(L4)を namespace 単位で表す方法。Claude Code のサンドボックスのドメイン許可は、設定単位(プロセス単位)で、namespace の概念はない。
- **推測**: L3 の別ユーザー運用は、herdr のセッションとソケットが同一ユーザー前提のため、セッションごとに別ユーザーの herdr を立てる形になる。実現性は未検証。
- **推測**: 認証の優先順位(環境の token が優先される)は、L0 で環境から token を外し、実行者側だけに持たせれば、agent 側で選ばれなくなる。

### 着手の可否の整理

- **着手可**: L0(認証を渡さない設計。公開操作を決定論の実行者に集める)、L1(役割別の deny。レビュー担当に Edit・Write の deny)、L2(補助)。ただし L1 は Bash 経由では抜けるので、「完全な強制」とは言わない。
- **試験可**: L3 のうちサンドボックス(Bash のみ。ファイルツールは L1 で別に守る)。
- **将来**: L3 の別ユーザー、L4。

## 検討した代替案

| 案 | 利点 | 欠点 |
|---|---|---|
| A. プロンプトの禁止だけ(現状) | 追加のコストがない。柔軟で、文脈に応じた説明ができる | 強制ではない。人の直接の依頼で外れる。読み取り専用のレビュー担当が書き換えた実例がある |
| B. すべての操作に人の承認 | 実装が単純。人が必ず見る | 人の負担が大きく、承認が形骸化する。agent の並列の利点が消える |
| C. agent ごとに VM やコンテナを分ける | 分離が最も強い。認証もネットワークも物理的に分けられる | 構築・運用のコストが高い。worktree や共有ツールとの連携が難しい。開発体験が落ちる。まず L0〜L3 で足りるかを見てからでよい |

## 結果(Consequences)

良い点:

- 禁止が文章でなくなり、人の直接の依頼や依頼文の抜けでも外れない操作が増える。
- 「持たせない」ので、迂回の検討(コマンドの別形)を考えなくてよい操作が増える。
- 公開操作が決定論の実行者に集まり、検査(方針、公開前の検査)を一箇所で行える。

悪い点:

- 構築コスト: 実行者の整備、役割別の設定、認証の分離が要る。
- 開発体験: 必要な操作が止まり、実行者への依頼の手順が増える。人の手作業が一時的に増える可能性もある。
- デバッグのしにくさ: 「なぜ失敗したか」が、権限設定・サンドボックス・認証のどれによるのか分かりにくい。止めた理由を出す仕組みが要る。
- L1 と L2 は迂回でき、単独では「強制」と呼べない。誤解を防ぐため、表の「抜け道」を設計文書に残す。

移行の段階(案):

1. 公開操作(push、PR 作成)の認証を agent から外し、決定論の実行者に集める(L0)。
2. 役割別の settings の deny(レビュー担当の書き込み禁止など)を入れ、プロンプトの「禁止」は補助に下げる(L1)。
3. Bash サンドボックスを役割限定で試す。サブエージェントへの適用を確認する(L3 の一部)。
4. 別ユーザー・egress filter は、1〜3 で不足が実測できたときに検討する(L3・L4)。

## 未解決の問い

- コマンド名による制限(L2)の抜け道を、どこまで許容するか。誤操作の予防としてのみ使うか、境界として扱うか。
- L3 の別ユーザー運用と、herdr のセッション(同一ユーザー、同一ソケット)の関係。ユーザーごとにセッションを分けると、人からの見え方や agent 間の連絡はどうなるか。
- egress filter の粒度(namespace 単位か、役割単位か、プロセス単位か)と、許可先の管理主体。
- 既存の設計との関係: 別途検討中の設計で案としている「役割ごとの deny」は L1 に当たる。点数による承認判定(allow / ask)は、操作が「許される場合の判定」であり、本 ADR の「そもそも持たせない」と層が異なる。両者の責務の境界(どこまでを環境で止め、どこからを承認で判定するか)を決める必要がある。
- サブエージェントへの権限・サンドボックスの適用(未確認の点)を、どの方法で検証するか。
