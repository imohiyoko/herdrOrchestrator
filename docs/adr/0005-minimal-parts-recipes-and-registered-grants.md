# ADR 0005: tb の部品を最小にし、組み合わせ(レシピ)と権限(操作の種類)を DB に登録できるようにする

- 状態: Accepted(2026-11-22。人が実装を依頼。下の「人が決めること」は推奨どおりで進める)
- 日付: 2026-11-22

## 要旨

- **困りごと**: 新しい使い道(例: agent を安全に再起動する手順)や新しい権限の種類を足すたびに、専用のコマンドと操作名をコードに書き、PR を出してマージするまで使えない。使い道は設定で作りたいが、いまの設定(`approvals` など)は、コードに既にある操作名を ask / allow に振るだけで、新しい種類は作れない。
- **決定(案)**:
  1. **部品は最小にする**: tb のコマンドは、1 つの副作用だけを持つ小さな部品に絞る。部品の一覧・引数の型・リスク階層は、コードの中に固定する。
  2. **組み合わせ(レシピ)は DB に登録する**: レシピは「部品の並び」だけ。任意のシェルは書けない。登録・変更は人だけができる。
  3. **権限の操作名も登録できるようにする**: レシピごとに `recipe:<名前>:<対象>` という操作名を、**1 つの汎用の判定の入口**で扱う。ask / allow は、既存の `approvals` と `grants` の glob で決める。
  4. **守りはコードに置く**: リスク階層は部品の最大から計算し、宣言で下げられない。人だけの部品はコード固定で、登録で緩められない。実行は依頼者の権限で、部品ごとに判定する。分からないときは実行しない(fail-closed)。すべて記録する。
- **段階**: 汎用の入口を 1 つ足す PR(コードの変更)を 1 回だけ出し、以降のレシピ・権限は設定で足す。この ADR は方針だけを決める。実装は、マージ後の別の PR。

## 状況(Context)

tb の権限は、次の 3 つの層でできている。

- **操作名**: 判定を呼ぶ箇所のコードに書かれている(例: `agent:stop:<名前>`、`send:<種類>:<宛先>`)。
- **ask / allow の割り当て**: `approvals`(操作名のパターン → ask / allow)、`grants`(誰が誰に何をしてよいか)、`delivery`(送信の扱い)で決める。
- **カタログ**: 操作名の説明(種別・副作用・リスク階層)を持つ。判定には使わない。コードの操作名がカタログに載っているかを、テストが双方向で確かめる。

このため、**新しい種類の操作を足すことは、コードの変更であり、公開 PR になる**。使い道が増えるたびに、(1)専用コマンドを足す、(2)操作名を足す、(3)カタログとテストを足す、が必要になる。

既存の `tb agent-restart` は、MCP が切れた agent の復旧(停止と、同じ会話での復活)のための専用コマンドで、idle / done でタスクが無いときに人や外から使う。ここで言う「自分の再起動」(agent が自分の pane の中から要求する手順)とは別の用途で、本 ADR はこの既存コマンドを置き換えない。

もう 1 つの困りごとがある。agent が自分の pane の中から自分を止める・再起動することは、pane の中の tb にはできない(自分を止めると、そのあとの手順が実行されない)。いまは、自分の再起動のような「pane の外で動く実行役」が必要な手順は、専用コマンドか、人の手作業になっている。

既にある仕組みは次のとおりで、それぞれ、レシピを置く場所になるかを検討した(代替案を参照)。

- **PR キュー**: agent が置く → 人が承認 → 外のジョブが実行。
- **定期ジョブの `COMMAND`**: scheduler が人の権限で実行する。
- **`approvals` / `grants` / `delivery`**: 既存の操作名への ask / allow の割り当て。
- **メッセージの差し替え**: 送信の中身の置き換え。

## 決定(Decision)

### 1. 部品(コードに固定)

部品は、次の性質を持つ、小さな操作である。

| 項目 | 内容 |
|---|---|
| 名前 | 部品の一覧に載っているものだけ。登録では増やせない |
| 副作用 | 1 つだけ。読み取りだけの部品、チケットを変える部品、agent を操作する部品、送信する部品、のように分かれる |
| 引数 | 型と値の検査をコードで持つ(例: agent 名の形、列挙された値)。型に合わない値は受け付けない |
| 対象 | レシピを実行する**依頼者自身**に固定できる。他者を対象にする部品は、別の操作名として判定する |
| リスク階層 | 部品ごとにコードが持つ(低・中・高・人だけ) |
| 人だけ | 人の端末からだけ実行できる部品(例: 報告の対応済み、PR キューの承認、設定の書き込み、agent の強制停止)は、**コードで人だけと固定**する。レシピの部品にはできるが、実行者が人でなければ止まる |

既存のコマンドは、この部品に分解できるものから、段階的に部品として整理する。専用コマンドは、足さない。既にあるものは残す。

### 2. レシピ(DB に登録)

レシピは、名前と、部品の並びである。

```
recipe: restart-agent        # 架空の例
  step 1: agent-status   target=$requester            # 読み取り
  step 2: wait-idle      target=$requester timeout=60
  step 3: agent-restart  target=$requester            # 外の実行役が行う
```

- **部品の並びだけ**。条件分岐・ループ・任意のシェルは書けない。引数は型の検査を通ったものだけ。
- 引数に使える変数は、`$requester`(依頼者)と、レシピが宣言した引数だけ。外から来た文字列をシェルに渡さない(実行はシェルを経由せず、部品を直接呼ぶ)。
- **登録・変更・削除は人だけ**(`tb recipe-set` など。名前は実装で決める)。agent の pane からは実行できない。変更の履歴を残す。
- 登録のときに、すべての部品が部品の一覧にあるか、引数が型に合うか、リスク階層が計算できるかを検査する。1 つでも通らなければ登録しない。

### 3. 権限(操作名の登録)

レシピの実行は、**1 つの汎用の入口**(例: `tb recipe-run <名前> ...`)で受ける。判定の操作名は、次の形にする。

```
recipe:<名前>:<対象>      例: recipe:restart-agent:worker-a
```

- ask / allow は、既存の `approvals` と `grants` の glob で決める(例: `recipe:restart-agent:* = ask`、`grants` に `lead-a recipe:restart-agent ~report`)。**判定の仕組みは増やさない**。
  - `grants` の行は、操作名を**最後の `:` で操作と対象に分け**、操作(`recipe:<名前>`)を glob で照合する。そのため、対象を含む `recipe:<名前>:*` とは書かず、対象を除いた `recipe:<名前>` と書く。`approvals` 側は操作名の全体を照合するので、`recipe:restart-agent:* = ask` の形でよい。
  - この分け方のため、**レシピ名にも対象にも `:` は使えない**。登録のとき、名前は文字種(英小文字・数字・`-` など、決まった範囲)と `:` を含まないことを検査する(段 2)。
- 登録されていない**レシピ名**は、既定で ask(既存の「一致なし」と同じ)ではなく、**実行しない**(fail-closed)。レシピを足すこと自体が、人の登録である。ここで「登録されていない」が指すのは**レシピ名だけ**で、対象は登録物ではない。対象は、`approvals` / `grants` の glob と関係(上司・部下など)で絞る(対象が許可の範囲外なら、既定の ask になる)。
- カタログに、レシピごとの項目(種別・副作用・リスク階層・allow の候補)を持たせてよい。ただし**判定の入力にするのは、コードが計算した値だけ**で、レシピの宣言ではない(次の守りを参照)。カタログの静的検査(コード中の操作名がカタログに載っているかを確かめるテスト)のため、レシピ全体を表す `recipe:*:*` の 1 行をカタログに置く(段 1〜2)。

### 4. 守り

1. **リスク階層は、部品の最大から計算する。宣言で下げられない。** レシピの定義に「低」と書いても、中の部品に高いものがあれば高になる。計算はコードが行い、登録された値は参考にしか使わない。
2. **人だけの部品は、コードで固定する。DB の登録で緩められない。** 登録で「この部品は誰でもよい」と書く欄を作らない。
3. **実行は依頼者の権限で、部品ごとに判定する。** レシピ全体の許可で、中の部品の判定を飛ばさない。依頼者が個々の部品を実行する権限を持たなければ、その部品で止まる。**レシピを許可することは、部品を許可することの代わりにならない**。
4. **対象は依頼者自身に固定する**のが既定。他者を対象にするレシピは、操作名の対象に他者の名前が入り、`grants` の関係(上司・部下など)で判定する。
5. **登録と変更は人だけ。** 登録した人・時刻・変更前後を記録する。
6. **fail-closed**: 部品の一覧にない部品、型に合わない引数、判定を読めない(台帳・設定が読めない)、実行役に届かない、のどれでも、**実行しない**。途中で止まったときは、どこまで済んだかを記録し、残りは続行しない(自動で巻き戻さない。人が見る)。
7. **記録**: 依頼者・レシピ名・対象・部品ごとの判定と結果を、チケットのイベント(ADR 0003 の `task_events`)に残す。誰がいつ何を実行したかが後から追える。
8. **スケジューラとの境界**: 定期ジョブが人の権限で動くことを使って、レシピの判定を迂回しない。定期ジョブからのレシピの実行も、依頼者(ジョブの持ち主として登録された agent)の権限で判定する。**ただし、いまの定期ジョブには持ち主・依頼者の概念が無い**。この守りを成り立たせるには、ジョブに持ち主を持たせる仕組みを段 3 で新設する必要がある(それまでは、定期ジョブからのレシピの実行を許さない)。人の権限で動かす場合は、ジョブの登録を人が行ったことを根拠にし、レシピの中の人だけの部品は、実行の時点でも人の承認を要する。

### 5. 外で動く実行役

pane の中の tb が自分を止められない問題は、**pane の外で動く短命の実行役**で解く。

- 実行役は、部品を並びどおりに呼ぶだけで、判断をしない。常駐しない(長寿にしない)。
- レシピの実行は、依頼者の pane の中で受け付けて判定し(ここまでは pane の中)、外の実行役に**検査済みの部品の並びだけ**を渡す。実行役が、渡された並びの外のことをしない。
- 実行役の起動は、既存の定期ジョブか PR キューの外のジョブの仕組みを使う。新しい常駐の仕組みは足さない。

## 検討した代替案

| 案 | 利点 | 欠点 |
|---|---|---|
| A. 現行の仕組みの延長(PR キュー・定期ジョブの `COMMAND`・`approvals` の割り当て) | 新しいコードが要らない | PR キューは PR の作成に特化している。定期ジョブの `COMMAND` は人の権限で動くので、人の承認を迂回する道になりうる。`approvals` は既にある操作名にしか効かず、新しい種類の権限は作れない |
| B. 使い道ごとに専用コマンドを足す | 1 つずつは単純。判定をコードで確かめやすい | 使い道のたびに PR が要る。コマンドが増え、部品の重複と判定の抜けが起きる。いまの困りごとそのもの |
| C. 長寿の実行役(常駐の agent が依頼を受けて実行する) | pane の外で動ける | 常駐の実行役が、広い権限を持つ入口になる。依頼者の権限で判定する守りが弱くなりやすい(実行役の権限で動いてしまう)。承認のすり抜け・権限昇格の経路になる |
| D. 外部の SDK・スクリプト言語でレシピを書かせる | 柔軟 | 任意の実行を許すことになり、リスク階層を計算できない。レシピの検査ができない |
| E. 部品とレシピを分けず、設定で任意のコマンド列を書かせる | 最も単純 | 任意のシェル実行と同じで、守りを置く場所がない |

## 結果(Consequences)

良い点:

- 新しい使い道は、人の登録(設定)だけで足せる。コードの PR は、汎用の入口を足すときの 1 回だけになる。
- 権限の判定の仕組みが 1 つ(既存の `approvals` / `grants`)のままで、新しい種類の権限は操作名の登録で足せる。
- リスク階層が部品から計算されるので、レシピを足しても、危険な操作が静かに低い階層に入らない。

悪い点・懸念:

- **権限昇格**: レシピの許可を通じて、本来は許されない部品が実行される経路にならないよう、部品ごとの判定を必ず残す必要がある。判定を飛ばす実装の誤りが、最も大きな危険である。
- **承認のすり抜け**: 人だけの部品を含むレシピが、人以外の権限で実行されないこと。定期ジョブ・外の実行役が人の権限を借りる経路を作らないこと。
- **任意実行**: レシピの引数や部品の中身に、外から来た文字列をそのまま渡さないこと。部品を直接呼び、シェルを経由しない。
- 部品の整理(既存のコマンドを部品に分ける)に、段階的な作業が要る。
- レシピが増えると、どのレシピが何を許しているかを人が把握しにくくなる。一覧と、効いている許可の出どころを出すコマンドが要る。

## 移行の段階(案)

実装は、この ADR のマージ後の、別の PR とする。

| 段 | 内容 | 人の関与 |
|---|---|---|
| 0 | この ADR(方針の決定)。コードの変更なし | ADR の承認 |
| 1 | 部品の一覧・引数の型・リスク階層の計算を、コードに足す(レシピはまだ登録できない)。人だけの部品の固定を、テストで確かめる | PR の承認 |
| 2 | レシピの登録・一覧・履歴(人だけ。名前は文字種と `:` 不可を検査)と、汎用の入口(判定と記録まで。実行は読み取りの部品だけ)。カタログに `recipe:*:*` の 1 行 | PR の承認 |
| 3 | 外の実行役と、副作用のある部品の実行。定期ジョブへの持ち主(依頼者)の概念の新設(守り 8 の前提) | PR の承認。最初のレシピは人が登録 |
| 4 | 最初のレシピ(agent の安全な再起動)を設定で作り、専用コマンドの案(自分の再起動のためだけの新しいコマンドを足す案。既存の復旧用コマンドは残す)を取り下げる | レシピの登録と、権限の割り当ては人 |

各段で、「人だけの部品がレシピ経由で緩まない」「リスク階層が下げられない」「部品ごとの判定が飛ばない」を、テストで確かめる。

## 人が決めること

1. **方向**: 専用コマンドを足し続ける(代替案 B)のではなく、部品・レシピ・権限の登録に進むか(推奨: 進む)。
2. **実行役**: pane の外の短命の実行役を、既存の定期ジョブの仕組みで置くか(推奨)、別の仕組みにするか。
3. **段階**: 段 1(部品の整理)から始めるか、段 2 の汎用の入口を先にするか(推奨: 段 1 から)。
4. **最初のレシピ**: agent の安全な再起動を最初の例にするか。

## 確認できていないこと・推測

- 既存のコマンドのうち、部品にそのまま分けられるものと、分け直しが要るものの割合は、数えていない。
- 外の実行役を、既存の定期ジョブの仕組みで置けるかは、設計の確認までで、動かしていない(**推測**)。
- 定期ジョブには持ち主・依頼者の概念が無い(守り 8 は、段 3 での新設が前提)。
- カタログの項目を判定の入力に使う場合の細部(どの項目をコードが計算し、どれを参考にするか)は、段 1 で決める。
