# ADR 0009: 既定の表を一番下の層にし、細かい主体の行が広い行と既定を上書きする

- 状態: Accepted(2026-11-27。人の依頼「既定は他の手段で自由に上書きできるロールであるべき」)
- 日付: 2026-11-27
- 置き換えるもの: ADR 0007 の決定 2「決め方: 当たる行のうち、いちばん厳しい効果を採る」(人が決めたこと 1)。同じ層の中ではこの決め方を残す

## 要旨

- **困りごと**: policy は「当たる行のうち、いちばん厳しい効果」で決まるため、`* gh:* * = deny`(全員に締める)を書くと、`@reviewer gh:approve o/* = allow` や `rev1 gh:approve o/* = allow` のような、役割や個別の agent に許す行が効かなかった。既定の deny を「全員の行」で明示した場合も同じで、既定が役割・個別の設定より強い層のように振る舞っていた。
- **決定**: 行の主体の書き方で層を決め、**細かい層の行が広い層の行と既定の表を上書きする**。
  1. 層(広い順): 既定の表(`perms/commands.tbl`・`perms/ops.tbl`)< 主体 `*`(`system:*`)< `@<役割>`・agent 名の glob(`w*`・`system:sched*`)< agent 名そのもの(`system:scheduler`)
  2. 当たる行(主体・操作・対象)のある、いちばん細かい層で決める。**同じ層の中では、今までどおり当たる行のいちばん厳しい効果**(行の順番は関係ない)
  3. 当たる行が 1 つも無ければ既定の表。既定の `deny` も、当たる行があれば必ず上書きされる
  4. 役割・関係を確かめられない行(台帳を読めない `@<役割>` など)は、今までどおり締める向きにだけ効く。ただし数えるのは、決めた層と、それより細かい層の行だけ(広い層の行は上書きされるので)
  5. 層は主体だけで決める。操作・対象の細かさ(`gh:*` と `gh:api`、`*` と `o/r`)は見ない

## 例

```
*        gh:*        *      = deny
@reviewer gh:approve my-org/* = allow
rev1     gh:merge    my-org/app = ask
```

- `@reviewer` の agent は `my-org/*` を approve できる(役割の層が `*` の層を上書き)
- `rev1` の `gh:merge my-org/app` は ask(個別の層)。ほかの `gh:*` は deny
- 役割の無い agent は、どの `gh:*` も deny

## 理由

- 人が思い描くのは「既定 → 全員 → 役割 → 個別」の順に上書きする設定で、権限の設定でよくある形(既定のロールを他のロールや個別の設定で上書きする)。
- ADR 0007 が「いちばん厳しい効果」を選んだのは、行の順番で抜け道ができないようにするためだった。層は主体の書き方だけで決まり、行の順番には依らないので、その性質は残る。
- 「全員を締めて、特定の役割・agent だけ緩める」が 1 行ずつで書ける。前は緩めたい相手を外すように広い行を書き直す必要があった。

## 代わりに失うもの・注意

- `* x * = deny` は、もう「誰にも許さない」を意味しない。細かい層の行が許せば通る。誰にも許したくない操作は、細かい層の行を書かない(policy を書けるのは人と、`policy:` を許された agent だけ。ADR 0007 の決定 2 の書く権限)。
- agent に policy を書かせている場合(`policy:<操作> <主体>` の allow)、その agent は自分が書ける主体の行で広い deny を上書きできる。前は「足せるのは締める行だけ」とみなせたが、今は緩める行も効く。`policy:` を渡すときは主体を絞る。
- `tb policy import` の確かめてほしい行: grants の行(主体を絞った行)は、approvals から変換した主体 `*` の行を上書きするので、「ask に当たる相手では許可にならない」とは出さない(主体 `*` の grants の行だけ出す)。

## policy で上書きできないもの(コードで固定。意図して残す)

次は policy の既定ではなく、コードの決まりなので、この ADR でも上書きできない。どれも「agent が自分の権限を広げる・人の判断を外す」のを止める安全装置として残す。

| 決まり | 場所 | 残す理由 |
|---|---|---|
| 人は常に通る、`human` の行は書けない | `internal/kernel/perms` | 人を締めると戻せなくなる |
| `unknown`(確かめられない呼び出し元)には何も許さない | 認証(ADR 0007 決定 1) | なりすましを止める |
| deny の記録 `Q-<n>` を例外として承認できるのは人だけ | `tb approval approve` | deny の例外を agent に開けさせない |
| `--always`(今後は承認なしにする)・`--all` 系・spawn-freeze 中の承認は人だけ | `tb approval approve` / `tb agent-approve` | 承認のついでに恒久の allow を書かせない |
| 自分の依頼は承認できない | `approve:` の判定 | 自己承認を止める |
| 自分の役割・`role:change` を許される役割の本文や対応を書けるのは人だけ | `tb role-write` / `tb role-set` | 役割を書き換えて自分の権限を広げるのを止める |
| 人だけの部品(レシピ) | `internal/recipe` の HumanOnly | 部品の定義として人だけ |
| `protect`(止めさせない agent) | ADR 0007 段 3b | 人も止める安全装置で、policy の外 |
| 設定を読めないときは deny | `internal/kernel/perms` | fail-closed |

一方、`git:push-force`・`gh:api`・`gh:secret-*`・`gh:auth-*`・`approve:*`・`policy:*`・`agent:flag` などの既定 deny は **既定の表の値** なので、この ADR で役割・個別の行から allow にできる。強制 push や token を出せる操作は危ないので、許すなら主体と対象(`owner/repo`)を絞って書く。
