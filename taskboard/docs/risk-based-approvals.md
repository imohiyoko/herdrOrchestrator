# リスク評価による承認判定(allow / ask)の設計

状態: 設計は決定済み。**第 1 段(評価を出すだけ)を実装済み**。第 2 段以降は別 PR。
対象: `taskboard/`(`tb send` と `tb approval`)。パスは断りがなければ `taskboard/` 起点。

## 1 結論

1. **方式は「点数方式の限定形」**。いまの `approval_of` は操作名の glob 照合だけで、本文・送信者・宛先の状態を見ない。
   「不明なときの値を項目ごとに決められる」「不明が 2 つ重なったら ask」を表せるのが点数方式だけなので、これを選んだ。ただし弱点を構造で抑える。
   - 「必ず ask にする」規則(拒否権)は点数に入れず別扱い
   - 合計ではなく**寄与を 1 件ずつ理由に列挙**する(列挙のない結果は作らない)
   - しきい値は 1 つ、点は整数 0〜しきい値
   - 評価は allow を自力で出さない(approvals.conf の ask を緩めない)
2. **最小の組**: R-07(評価不能は ask。常時)+ R-02(本文の破壊的・公開系の語)+ R-06(宛先が停止中。状態・役割が不明な場合は `[unknown]` が扱う)。
   R-01 / R-04 / R-05 は候補で既定は無効。R-03(秘密検査)は任意。
3. **不明時の既定**: 役割・宛先の状態は ask、モデルは 1 点(単独では通る)。
4. **緩める方向の設定は第 3 段まで効かせない**(読み込んで警告するだけ)。
5. 決定論(時刻・乱数・LLM を使わない)、fail-closed(評価できなければ ask)を維持する。

## 2 入力(属性)と信頼度

| 属性 | 信頼度 | 取り方 | 不明になる場面 |
|---|---|---|---|
| 送信者の名前 | (a) 確か | pane から `herdr agent list` で決める(自己申告にしない) | 引けなければ送信自体が終了 3(評価に来ない) |
| 送信者の役割 | (a) | `roles/map.conf` / 台帳 `agents.role` | map.conf に一致なし |
| 送信者のモデル | (a') 台帳値(不完全) | `agents.model` | tb 以外で起動した agent は NULL |
| 宛先の役割・状態 | (a) | 役割は同上、状態は台帳 `agents.state` | 一致なし・台帳に行がない |
| kind | 列挙検査済み(送信者の選択) | `--kind` | 不明にならない |
| 本文 | (b) 嘘ありうる | `--text` | 本文なしは評価不能 |

本文の語境界は ASCII 限定。日本語に隣接した語も検出する(locale に依存しない)。

原則: **(b) 送信者が書く値は、評価を緩める根拠にしない。厳しくする方向にだけ使う。** 本文に危険語があれば ask に寄せるが、危険語が無いことは allow の根拠にしない(書式を変えれば抜けられるため)。

台帳のモデルは「tb が起動時に指定した値」で、実行中のモデルの証明ではない。モデルを条件にする規則(R-01)は、モデルの取り方が固まるまで有効にしない。

本文の検査には、シェル構文向けの既存検査(`proxy-check` の危険構文検出)を流用しない。自然文の `&` `$` `;` `>` を危険と見なし、ほぼ全件が ask になるため。本文検査は専用の関数で、語彙は規則ファイルに持つ。

## 3 出力

- 値: `allow` / `ask`。**deny は評価では出さない**(deny は `routes.conf` の `!` 規則の仕事)。
- 付随: 寄与 1 件 = 1 行(規則 ID または `unknown:<属性>`、点数、理由文)、合計としきい値、警告。
- 寄与の出し方は決定論: 不明な属性 → 組み込みの規則 → 規則ファイルの規則(上から)の順。

### 3.1 既存(approvals.conf)との関係

| approvals.conf | リスク評価 | 最終 |
|---|---|---|
| ask | (何でも) | ask |
| allow | ask(拒否権、または合計 ≥ しきい値) | **ask**(第 2 段から) |
| allow | 通過 | allow |
| 一致なし(既定 ask) | 通過 | ask(評価の通過は ask を覆さない) |
| どれか | 評価不能 | ask(設定で緩められない) |

評価は決して approvals.conf を緩めない。**第 1 段では最終判定に使わない**(`approval_of` の結果は変わらない)。

### 3.2 第 1 段の出力

`tb approval <操作> --to <宛先> --text <本文> [--kind K]` は、従来の 2 行(`ask|allow` と `rule:`)と終了コードをそのままに、続けて次を出す。

```
risk: ask            # 第 1 段の参考値。最終判定には使われない
risk-score: 3 / threshold 2
risk-reason: R-02 +ask 本文に破壊的・公開系の操作語(語: push)
risk-reason: unknown:sender.model +1 sender.model が不明(設定 risk:1)
risk-warn: 緩め設定は第 3 段まで無効: ...
```

送信者が人かどうか(pane の有無)の判定は、既存の `require_human` と同じ前提(`HERDR_PANE_ID` が空なら人)。`tb send` は pane から送信者を決めるので、この前提の影響は `tb approval` の参考表示だけに限られる。第 2 段で、人として評価されることが「緩む」方向に働く規則を足さない。

`--to` と `--text` を付けない `tb approval <操作>` は、従来の出力のまま(評価なし)。

`tb send` は、outbox の `reason` の末尾に 1 行の評価
(`risk: ask(参考。score 3/2) [R-02 +ask ...; ...]`)を追記する。スキーマは変えない。
`status`・終了コード・配送は評価に影響されない。

## 4 設定

- 置き場所: `config/risk-rules.conf`(人が編集。gitignore)。ひな形は `config/risk-rules.conf.example`。
- **場所は固定。環境変数では差し替えられない**(agent が自分の許可ファイルで評価させる迂回を作らない)。テストは、評価ライブラリを別のシェルで読み込み、その中で変数を代入して差し替える。
- 既定は tb のコード内に持ち、ファイルは上書きだけ(ファイルが無い/読めなければ既定で動く。既定は緩くない)。
- 編集は人だけ。tb に編集コマンドは作らない。
- 構文エラー・未知の条件語・範囲外の点・不正な正規表現・空文字列に一致する正規表現は、評価不能(R-07)として ask。

```
[threshold]
ask-at = 2

[unknown]                       # ask | allow | risk:<整数>
sender.model = risk:1

[patterns]                      # 名前付き正規表現(ERE。語境界つき)
destructive = drop table        # 既存の名前には「足す」だけ

[rules]                         # <ID> | <条件> | <ask または risk:N> | <理由>
R-04 | body.matches(external) and target.role in (worker) | risk:1 | 外部送信を含む依頼
```

- 値: `ask` = 拒否権(点数に関係なく ask)、`allow` = 0 点、`risk:N` = N 点。
- 条件の語彙は固定の小さな集合(`body.matches(<名前>)` / `body.secret` / `sender.role` / `target.role` / `target.state` / `kind` の `in (...)`)。設定で任意のシェル式や正規表現そのものを実行させない(名前付きパターンの中身だけ別に持つ)。
- **規則の条件が不明な属性を参照したら、その条件は「一致しない」**。不明の扱いは `[unknown]` で 1 回だけ数える(二重に数えない)。

### 4.1 規則

| ID | 条件 | 結果 | 位置づけ |
|---|---|---|---|
| R-07 | 評価に必要な入力が取れない/設定が壊れている | ask | **組み込み・常時・外せない** |
| R-02 | 本文が `push` / `merge` / `--force` / `--approve` / `reset --hard` / `rm -rf` を含む(語境界) | ask | **組み込み(最小の組)** |
| R-06 | 宛先が停止中 | risk:2 | **組み込み(最小の組)** |
| R-01 | 送信者モデルが軽量系 × 宛先が外部送信できる役割 | risk または ask | 候補。モデルの取り方が決まってから |
| R-03 | 秘密検査が本文で 1 件以上(種類名だけ表示) | ask | 任意。主な担保は別の仕組み(7 章) |
| R-04 | 本文が外部送信・URL を含む × 宛先が worker | risk:1 | 候補。誤検出が多そう |
| R-05 | 送信者が worker × 宛先が worker(横の連絡) | risk:1 | 候補。役割の定義待ち |

R-02 を選ぶ理由: 被害が大きい操作語だけを狙い、語が少なく理由が自明。誤検出は ask に倒れるだけで、許可が増える方向のリスクが無い。
R-06 を選ぶ理由: 台帳の状態だけで決まり、本文の書式で回避されない。

### 4.2 不明時の既定(`[unknown]`)

| 属性 | 既定 | 理由 |
|---|---|---|
| sender.role / target.role / target.state | ask | 取れて当然の値。不明は何かが壊れている合図 |
| sender.model | risk:1 | 台帳に NULL がありうる。単独では通し、不明が重なれば ask |

不明が効いたときは必ず `unknown:<属性>` の寄与行を出す(0 点でも出す)。
**既定より緩い値(しきい値を上げる、`[unknown]` を既定より弱くする)は第 3 段まで効かず、警告だけ**出す。厳しくする方向(しきい値を下げる、`ask` に上げる)は第 1 段から効く。
入力の「取れなかった」(未設定。R-07)と「取れたが不明」(空。`[unknown]`)は別物で、前者は設定で緩められない。

## 5 監査役に任せる範囲(案。実装は別途)

- ルールの変更は**提案として出す**(監査役は直接変更しない)。根拠は outbox(状態・reason の人の承認/却下)、`approval_changes` など既存の履歴。
- 例: 「直近すべて人が承認した操作 → allow 候補」「R-02 が ask を出したが全部承認された → 語を絞る候補」「`unknown:*` が頻発 → 台帳の穴を直す候補」。
- **自分の権限や承認ルールを広げる提案は特別扱い**: 専用の種別、宛先は人、自動適用の経路を作らない。
- 過去の送信にルールを当てる dry-run は可能だが、送った時点の役割・状態・評価結果が履歴に無く、現在値での近似になる。第 1 段で reason に評価を残すので、以後は材料が増える。
- 秘密らしき文字列の検査は、**別の仕組み(エージェントと LLM API の間に置くプロキシ)で担保する**。tb 側の R-03 は任意の二重化にとどめる。
  代わりに、**監査役がそのプロキシの設定(検出ルールの網羅、許可リストの広さ、fail-closed の挙動、更新への追従)を読み取りのみで監査する**。報告には検出パターンの全文・実際の秘密・内部のホストや URL を書かない(構造と ID だけ)。

## 6 リスク

1. **ルールが緩いと全部 allow になる**: しきい値を上げる/点を 0 にする/`[unknown]` を allow にすると全体が緩む。対策: 拒否権は点数に入らない、しきい値の上限と点の範囲を検査する、緩め設定は第 3 段まで効かせない、第 3 段以降で効いたときは理由に必ず出す。
2. **agent が評価を迂回する経路**:
   - env の差し替え: tb は呼ぶ agent 自身のプロセスで動くため、設定ファイルの場所を env で変えられると自分の許可で評価させられる。→ **規則ファイルは env で差し替えられない**(本実装)。ただし既存の `TB_APPROVALS` などは現状のまま。
   - `herdr agent prompt` を直接打つ: tb も評価も通らない(約束であって強制ではない)。
   - 本文の書式を変えて危険語を避ける: 語彙検査は必ず抜けられる。だから「本文は緩める根拠にしない」。
   - 申告の嘘、DB への直接書き込み。
3. **評価ロジックと設定を agent が書き換えられない担保**: agent の設定で `config/`・`lib/`・`roles/` への書き込みを deny する(人が入れる)、ファイルの所有者・権限を分ける、規則ファイルのハッシュを記録して変化を検知する、など。**第 2 段は厳しくする方向だけなので被害は限定的。第 3 段は、この担保が済むまで入れない。**

### 決定済みの点(推奨を採用)

- 迂回対策: 規則ファイルは env で差し替えない作りにし、agent の設定での deny は人が入れる(第 2 段の前)。
- モデル情報: 第 1 段は台帳 + `[unknown]` の `sender.model = risk:1`。モデル条件の規則は有効にしない。必要になれば hook でモデルを記録する(別途)。
- 履歴の列(送信者の役割・モデル、評価結果)は、第 2 段の頃に足す。
- ルール提案の宛先は人(専用の種別。設定役を経由しない)。
- 第 3 段でも、評価は approvals.conf の既定 ask を上書きできない(approvals.conf が allow の範囲内だけ)。
- 秘密らしき文字列の検査(R-03)は任意で既定は無効。入れるときは ask。deny は `routes.conf` に任せる。
- 適用範囲は、まず `tb send` と `tb approval` だけ。
- 不明時設定の緩めは、第 3 段まで効かせない。効いたら理由に出す。
- 方式は点数方式の限定形。

## 8 将来の拡張点: namespace

agent ごとに namespace を切り分け、namespace ごとに egress filter を立てる予定がある(未実装)。評価の入力に `namespace` 属性を足せる形にしておく。
不明のときは `[unknown]` に乗る(今は常に不明 = allow で 0 点。filter が入った後に人が引き上げる)。
属性が増えても、評価の構造(寄与の列挙・拒否権・しきい値)は変わらない。
namespace を tb が割り当てるなら (a)(確か)、agent が自分で名乗るなら (b)(厳しくする方向にだけ使う)。
