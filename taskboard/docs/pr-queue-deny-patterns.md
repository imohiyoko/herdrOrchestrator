# pr-queue の公開前検査

`tb pr-queue run` は、PR を作る前に、次の 5 つに規則ファイルを掛けます。

| 対象 | 位置の表記 |
|---|---|
| PR の題 | `title` |
| PR の本文(行ごと) | `body:<行>` |
| コミットメッセージ(base からブランチまでの各コミット、行ごと) | `commit <hash7>:<行>` |
| コミットの author / committer(名前とメール) | `author <hash7>` / `committer <hash7>` |
| ブランチ名 | `branch` |
| 差分: 変更したファイルのパス(引用符なしの生のパス名。非 ASCII も) | `path#<n>`(n は変更ファイルの番号) |
| 差分: 足した行 | `diff#<n>:<行>`(n はファイルの番号。`path#<n>` と同じ順) |

位置はパス名そのものではなく番号で出します(パス名に規則語が含まれていても、値を通知や記録に出さないため)。

## 設定(必須)

- `config/pr-queue.conf`(`<tb>/config/` の固定の場所)の `deny_patterns` に、規則ファイルの**絶対パス**。人だけが書く。
- **環境変数(`PR_QUEUE_DENY_PATTERNS` / `PR_QUEUE_DENY_EXCEPTIONS`)や `PR_QUEUE_CONF` では決められません**(差し替えの口を作らない。ADR 0001)。環境変数が設定されていると警告して無視します。
- **未設定・読めない・書式が不正・規則が 0 件なら、`run` は何もせず警告して終了コード 1 で止まります(fail-closed)。** 承認済みの行はそのまま残ります。公開か非公開かの判別はしないので、許可リストのリポジトリすべてに掛かります。
- 規則ファイルは社内の名前を含みうるので、この公開リポジトリには置きません。

## 規則ファイルの書式

1 行 1 規則: `<名前> <フラグ> <パターン(ERE)>`。`#` で始まる行と空行は無視。フラグは `i`(大文字小文字を無視)か `s`(区別する)。

```
example-name  i  example-word
example-key   s  AKIA[0-9A-Z]{16}
```

## 例外ファイル(任意)

conf の `deny_exceptions`(絶対パス)。1 行 1 例外: `<規則名> <ERE>`。その規則に合った**文字列(ヒットした部分)**が ERE に合えば、そのヒットは無視します(大文字小文字の扱いは規則と同じ。厳密にしたいときは `^` と `$` を書く)。空文字列に合う例外(`.*` など)は設定エラーで、run は止まります。

noreply の Co-Authored-By 行を通す例(`email` という名前の規則がある場合):

```
email  ^noreply@example\.com$
```

## 検査の対象は origin の今の内容

`run` は検査の直前に、`git ls-remote` で origin のブランチの SHA を取り、ブランチと `main` を `git fetch` で追跡参照(`refs/remotes/origin/*`)に取り込み、追跡参照の SHA が origin と一致しなければ止めます。検査と差分のガードは追跡参照だけを見ます(clone のローカルブランチは使いません)。承認の後に別の clone から force push された内容も、検査してから PR になります。

- origin にブランチが無い → 却下。
- ls-remote・fetch の失敗、取り込み後に origin が変わった(SHA 不一致) → その行は触らず(attempts も使わず)次の回に回します。
- `approve` も同じ同期をしてから差分のガードを掛けます。
- バイナリの変更(`git diff --numstat` が `-\t-`)は内容を検査できないので、`.github/workflows` の変更と同じく人に回します(承認も run も通さない)。

## ヒットしたとき

PR は作らず、行を `rejected`(`last_error` に「公開前検査: 規則名@位置」)にします。attempts は使いません。`tb notify` が on のときは、規則名と位置だけを警告として 1 件積みます。**マッチした値は、出力にも DB にも通知にも出しません**(位置は番号なので、パス名も出ません)。直したら登録し直します。

## 完全には閉じられない隙(既知の限界)

- **検査したあと PR になるまでの時間差。** run は、検査の直前と `gh pr create` の直前の 2 回 `ls-remote` で origin の SHA を取り、検査した SHA と違えば作らず次の回に回します。それでも、2 回目の確認から `gh pr create` が head を解決するまでの短い間に push し直されると、検査していない内容が PR になりえます(`gh pr create` に SHA を固定して渡す口が無いため)。
- **同一 OS ユーザーの限界。** 固定の `config/pr-queue.conf` も規則ファイルも、同じ OS ユーザーなら書けます。deny の規則ファイルは conf の固定キーで決まり、env では差し替えられませんが、書き換えそのものは防げません。OS の権限分離(ADR 0001 の L0・L3)の課題です。
- **`PR_QUEUE_CONF` による conf の差し替え。** deny 以外のキー(`auto_approve`、`branch_prefixes` など)は `PR_QUEUE_CONF` で別の conf に差し替えられます。`auto_approve` を 1 にすると、scan が人の approve なしで `approved` を積めます(既定は 0。人が設定に書くまで効きません)。人の決定で、今回のコードでは直していません。

## この検査がしないこと

- 規則ファイルによる検査は `approve` と `scan` では掛けません(run の直前だけ。差分のガードは approve でも掛かります)。
- 検査の範囲外: PR 本文以外の PR の属性(ラベル・assignee など)、ファイルのモード・シンボリックリンクの先、`.gitattributes` 経由のフィルタ。
- PR の作成後に本文が編集されることは見ません。
